# Research: backend platform & datastore survey

**Issue:** [#8](https://github.com/icoffiel/ff-pickem/issues/8) — Research: backend platform & datastore — Postgres vs Convex vs alternatives
**Question:** Is "Postgres + host + Auth.js + external cron" (the assumption baked into #4) the right backend, or does a batteries-included platform fit this app better? Survey Postgres-baseline, Convex, Supabase-as-BaaS, Firebase/Firestore, and 1–2 others, scored specifically against this app's needs.

## Recommendation

**Convex**, with **Supabase (used as a full BaaS, not just a Postgres host)** as the strong second choice if staying relational matters more than collapsing moving parts.

This app's defining pressure is that two of the seven scoring axes — **real-time** ("who's picked," live standings) and **scheduled grading** — are first-class product requirements, not nice-to-haves, and the original plan (#4) solves both by bolting on external infrastructure (no realtime story at all; GitHub Actions cron for grading). Convex makes both free, built-in, and effectively zero-config: `crons.ts` replaces the GitHub Actions workflow ([docs.convex.dev/scheduling/cron-jobs](https://docs.convex.dev/scheduling/cron-jobs)), and every query is reactive by default, so "live standings" needs no extra plumbing, no Pusher/Ably account, and no Postgres LISTEN/NOTIFY hand-rolling. Convex Auth also reuses the *exact* Resend provider config from #3 ([github.com/get-convex/convex-auth — email.mdx](https://github.com/get-convex/convex-auth/blob/main/docs/pages/config/email.mdx)), so the #3 finding survives almost verbatim even though the surrounding Auth.js/NextAuth framework itself is replaced.

**The biggest trade-off:** Convex's document model has no SQL `GROUP BY`. Standings aggregation (a Membership's picks, correct/incorrect, joined across weeks and games) becomes hand-written TypeScript that walks indexes and reduces in code ([docs.convex.dev/database/reading-data](https://docs.convex.dev/database/reading-data)), instead of one SQL query. At this app's scale — a private league, dozens of members, a few hundred picks a week — that's a real but small cost: it's a different idiom, not meaningfully more code, and it doesn't require denormalized counters the way Firestore would. If the team would rather keep the relational data model and its tooling (Prisma/Drizzle, `GROUP BY`, standard SQL portability) and is willing to accept a manual-restore risk on a paused free project, **Supabase full BaaS** is the right fallback: it keeps every strength of the Postgres baseline while *also* picking up built-in Realtime and built-in Cron, closing both of #4's gaps without leaving the relational model.

Both recommendations **supersede #4's Neon + GitHub Actions cron pairing**. Neither forces abandoning #3 (Resend) — see the per-option "keeps/supersedes" notes below for exactly which parts of #3 survive vs. get replaced by a platform-native equivalent.

## Per-option detail

### Postgres baseline (Neon/Supabase-as-host + Prisma or Drizzle)

This is #3 + #4 as already researched and closed — included here as the control group.

- **Data-model fit:** best possible — the domain (User/League/Membership/Game/Pick, standings via aggregation) is exactly what relational `GROUP BY` was built for.
- **Real-time:** nothing built in. Neon and vanilla Postgres have no live-query mechanism exposed to a Next.js app; you'd need a separate pub/sub layer. Pusher's free "Sandbox" plan (100 concurrent connections, 200,000 messages/day) is a viable bolt-on, but it's dev/test-oriented positioning, not a guaranteed production SLA. Source: [pusher.com/channels/pricing](https://pusher.com/channels/pricing/).
- **Scheduled grading:** GitHub Actions cron, per #4 — external, 5-minute floor.
- **Auth:** Auth.js + Resend, per #3, unchanged.
- **Free tier:** Neon free — 0.5GB storage, 100 CU-hrs/mo/project, autosuspend after 5 min idle but auto-wakes on next query. Source: [neon.com/pricing](https://neon.com/pricing) (already cited in #4).
- **Lock-in:** best of any option — pure SQL, `pg_dump`-portable, swap hosts freely.
- **Build simplicity:** worst — every capability (host, DB, ORM, cron, realtime) is a separate vendor to wire and monitor.

### Convex

- **Data-model fit:** Convex is a document database with TypeScript query functions, not SQL. Joins are index lookups plus `Promise.all`, e.g. querying `attendees` by an index on `eventId` and then fetching each related `user` by ID ([docs.convex.dev/database/reading-data](https://docs.convex.dev/database/reading-data)). For standings (Pick → Membership → Game), this is a few index-driven queries composed in code rather than one SQL statement. At league scale (tens of members, low thousands of Pick rows/season) this is not a performance or complexity concern — but it is a different idiom, and it's the one place this option scores below Postgres/Supabase on the ticket's own rubric.
- **Real-time:** built-in and the headline feature — Convex queries are reactive by default; no separate real-time service, no manual subscription wiring. (Source: Convex's own positioning as "a reactive database" across [docs.convex.dev](https://docs.convex.dev) and the resolve-library description: "real-time database, serverless functions, and file storage.")
- **Scheduled grading:** built-in via `convex/crons.ts`. Supports `crons.interval()` (as fine as `{ seconds: 30 }`), `crons.cron()` (standard 5-field cron string, minute granularity), and `crons.monthly()`. Source: [docs.convex.dev/scheduling/cron-jobs](https://docs.convex.dev/scheduling/cron-jobs).
- **Auth:** Convex Auth (`@convex-dev/auth`) explicitly reuses Auth.js *provider configs* — its email/magic-link doc shows importing `Resend` straight from `@auth/core/providers/resend` and wiring it into `convexAuth({ providers: [Resend] })`. Source: [github.com/get-convex/convex-auth — email.mdx](https://github.com/get-convex/convex-auth/blob/main/docs/pages/config/email.mdx). This is not the Auth.js *database-adapter* pattern (no NextAuth session/JWT layer) — Convex Auth is its own session system that happens to borrow Auth.js's provider config shape. Convex also supports wiring in a fully external/third-party auth provider (e.g., Clerk, Auth0, or a custom JWT source) via `ConvexProviderWithAuth`, so Auth.js/NextAuth-with-JWTs is not strictly precluded either. Source: [docs.convex.dev/auth/advanced/custom-auth](https://docs.convex.dev/auth/advanced/custom-auth).
- **Free tier:** 0.5GB database storage, 1,000,000 function calls/mo, 1GB data egress/mo, 20 GB-hours of action compute, 1GB file storage, teams of 1–6 developers. Source: [convex.dev/pricing](https://www.convex.dev/pricing).
- **Lock-in / portability:** Convex open-sourced its backend — self-hostable as a Docker container, storing data in SQLite or pointed at Postgres, under an FSL license that auto-converts to plain Apache-2.0 two years after each release. `npx convex export` / `npx convex import` move data between self-hosted and cloud deployments. Source: [docs.convex.dev/self-hosting](https://docs.convex.dev/self-hosting), [github.com/get-convex/convex-backend](https://github.com/get-convex/convex-backend). This meaningfully de-risks the "proprietary platform" concern relative to Firestore.
- **Build simplicity:** best of the group — one platform provides the database, server functions, real-time, scheduled jobs, and (via Convex Auth) the auth session layer. The Next.js frontend still deploys to Vercel; #4's hosting choice for the *frontend* survives.

### Supabase (as a full BaaS)

- **Data-model fit:** best — it's managed Postgres, so the relational model and `GROUP BY` standings queries carry over unchanged from the baseline; Prisma or Drizzle both work against it normally.
- **Real-time:** built-in — Supabase Realtime streams Postgres changes (and offers Broadcast/Presence channels) directly to clients. Free plan: 200 concurrent connections, 2,000,000 messages/mo. Source: [supabase.com/pricing](https://supabase.com/pricing).
- **Scheduled grading:** built-in via Supabase Cron, a dashboard/SQL wrapper around the `pg_cron` Postgres extension — `cron.schedule('name', '*/5 * * * *', $$ ... $$)`, minute-level granularity, can call a database function, an Edge Function, or an arbitrary webhook. Supabase's guidance: no more than 8 jobs running concurrently, each under 10 minutes. Source: [supabase.com/docs/guides/cron](https://supabase.com/docs/guides/cron), [supabase.com/docs/guides/database/extensions/pg_cron](https://supabase.com/docs/guides/database/extensions/pg_cron). The pricing page does not list Cron as a paid add-on or gate it to Pro+, unlike Realtime/Edge Function invocation *quotas* which do scale by plan — source: [supabase.com/pricing](https://supabase.com/pricing).
- **Auth — two viable paths:**
  1. **Keep #3 exactly:** Auth.js + the official `@auth/supabase-adapter` (stores sessions/verification tokens in a `next_auth` Postgres schema) + the same Auth.js `Resend` email provider from #3. Source: [authjs.dev/getting-started/adapters/supabase](https://authjs.dev/getting-started/adapters/supabase).
  2. **Use native Supabase Auth** (its own magic-link flow) with Resend wired in as a custom SMTP provider — Resend has a documented one-click Supabase integration for exactly this. Source: [supabase.com/blog/supabase-integrations-marketplace](https://supabase.com/blog/supabase-integrations-marketplace); the send-path itself can also be done via a Supabase Auth email hook calling the Resend API. Source: [supabase.com/docs/guides/functions/examples/auth-send-email-hook-react-email-resend](https://supabase.com/docs/guides/functions/examples/auth-send-email-hook-react-email-resend).
- **Free tier:** 500MB database storage, 50,000 MAU, 5GB egress + 5GB cached egress, 500,000 Edge Function invocations/mo, limit of 2 active projects. **Free projects pause after 1 week of inactivity, and — per #4's existing finding — resuming requires a manual dashboard/API restore, with no documented auto-wake.** This is the one real operational risk for a weekly-cadence pick'em app. Source: [supabase.com/pricing](https://supabase.com/pricing), and #4's finding citing [supabase.com/docs/guides/platform/going-into-prod](https://supabase.com/docs/guides/platform/going-into-prod).
- **Lock-in / portability:** strong — underneath the platform features is a real Postgres connection string; Realtime, Edge Functions, and Auth are all optional layers, so you can adopt only the pieces you want and fall back to treating it as "just Postgres" (i.e., degrade gracefully toward the baseline option) if the BaaS features disappoint.
- **Build simplicity:** one platform replaces Neon + GitHub Actions + a realtime vendor, but the weekly-pause behavior means a solo dev must actively manage project activity (e.g., a lightweight weekly keep-alive ping) to avoid a manual-restore surprise on game day.

### Firebase / Firestore

- **Data-model fit:** weakest of the mainstream options. Firestore has no cross-collection JOIN or `GROUP BY`; Google's own guidance for relational-shaped data is to denormalize into subcollections and keep documents lightweight, restructuring around query access patterns rather than normalizing. Source: [firebase.google.com/docs/firestore/data-model](https://firebase.google.com/docs/firestore/data-model). For standings this likely means maintaining denormalized counters via transactions/triggers rather than a simple aggregation query — more moving parts than either the SQL or Convex-index approach.
- **Real-time:** built-in and mature — `onSnapshot()` listeners push live updates for both local and server-side writes. Source: [firebase.google.com/docs/firestore/query-data/listen](https://firebase.google.com/docs/firestore/query-data/listen).
- **Scheduled grading:** Cloud Functions (any generation, including scheduled/`onSchedule` functions) require the **Blaze** (pay-as-you-go) plan — they are simply unavailable on the free Spark plan, even though Blaze itself includes a no-cost usage quota and the first 3 Cloud Scheduler jobs/account are free. Source: [firebase.google.com/docs/projects/billing/firebase-pricing-plans](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans), [firebase.google.com/docs/functions/schedule-functions](https://firebase.google.com/docs/functions/schedule-functions). This can be sidestepped by keeping the grading job as a Vercel API route (using the Firebase Admin SDK against Firestore) triggered by the same GitHub Actions cron from #4 — Spark-plan Firestore read/write quotas apply either way — but that means Firebase isn't actually solving the scheduling gap; #4's cron design just gets reused unchanged.
- **Auth:** Firebase Authentication's email-link (passwordless) sign-in is sent through Firebase's own delivery pipeline; the fetched docs give no option to redirect that send through a third-party provider like Resend. Source: [firebase.google.com/docs/auth/web/email-link-auth](https://firebase.google.com/docs/auth/web/email-link-auth). To keep #3's Resend choice, you'd bypass Firebase Auth entirely and use Auth.js with the official Firestore adapter (`@auth/firebase-adapter`, uses the Firebase Admin SDK) — source: [authjs.dev/getting-started/adapters/firebase](https://authjs.dev/getting-started/adapters/firebase) — which somewhat defeats the point of choosing Firebase for its auth story.
- **Free tier (Spark):** Firestore — 50,000 reads/day, 20,000 writes/day, 20,000 deletes/day, 1GiB total storage; Cloud Functions unavailable (see above). Source: [firebase.google.com/pricing](https://firebase.google.com/pricing).
- **Lock-in / portability:** weakest of the mainstream options — Firestore's document/subcollection shape is Firestore-specific and typically denormalized around Firestore's query constraints, making a later migration a real data-model rewrite, not just a connection-string swap.
- **Build simplicity:** medium — mature SDKs and docs, but the denormalization work for standings and the Blaze-plan detour for scheduling add real solo-dev effort that the other options avoid.

### PlanetScale (surfaced, ruled out)

PlanetScale dropped its free "Hobby" tier in April 2024 and has not reintroduced one for either MySQL or its newer Postgres product; the cheapest Postgres option (`PS-5`, non-HA, arm64) starts at **$5/month**. Source: [planetscale.com/pricing](https://planetscale.com/pricing). Given the "no budget for paid tiers" constraint, this fails the very first filter regardless of its otherwise-strong relational data-model fit and mature branching/schema-change tooling — not evaluated further.

### PocketBase (surfaced, ruled out)

PocketBase is a single self-hosted Go binary bundling SQLite, realtime subscriptions, file storage, and its own auth (email/password and OAuth2 out of the box) — source: [pocketbase.io](https://pocketbase.io/). It has genuine strengths here: SQLite still supports joins, its subscriptions are realtime-native, and (per PocketBase's broader docs, not independently re-verified here beyond the homepage) it supports scheduled jobs via Go/JS hooks and SMTP configuration that could plug in Resend as the relay. The disqualifying issue is **hosting**, not features: PocketBase needs a persistent, long-running process with a writable disk for its embedded SQLite file — the opposite of the serverless model #4 already chose (Vercel Hobby functions) and the opposite of every free-tier host #4 evaluated and rejected for exactly this reason (Render free tier sleeps after 15 min idle; Railway's "free" tier is a 30-day trial credit). Adopting PocketBase would reopen the hosting question #4 already closed, for a datastore that (unlike Convex or Supabase) has no managed-serverless free offering of its own. Not recommended.

## Keeps / supersedes #3 and #4

| Option | #3 (Resend) | #4 (Vercel + Neon + GitHub Actions cron) |
|---|---|---|
| **Postgres baseline** | **Keeps** — unchanged | **Keeps** — this option *is* #4 |
| **Convex** | **Keeps the provider** (Resend, via Convex Auth's reuse of the Auth.js Resend config) — **supersedes the Auth.js/NextAuth framework** itself | **Supersedes** Neon and GitHub Actions cron entirely (Convex is DB + functions + cron); Vercel likely still hosts the Next.js frontend |
| **Supabase full BaaS** | **Keeps fully** if using Auth.js + `@auth/supabase-adapter` + Resend; **keeps the provider only** (via custom SMTP) if using native Supabase Auth | **Supersedes** Neon (→ Supabase Postgres) and GitHub Actions cron (→ `pg_cron`/Supabase Cron); Vercel hosting choice unaffected |
| **Firebase/Firestore** | **Supersedes** if using native Firebase Auth (can't route through Resend); **keeps** only by bypassing Firebase Auth via Auth.js + Firestore adapter | **Supersedes** Neon (→ Firestore); GitHub Actions cron can be **kept** (calling a Vercel/Firebase Admin SDK route) since Cloud Functions need the paid Blaze plan anyway |
| **PlanetScale** | **Keeps** — unaffected | **Supersedes** only the Neon piece — but fails the free-tier requirement outright, so moot |
| **PocketBase** | **Keeps the provider** (Resend as SMTP relay) — supersedes Auth.js as a framework, same as Convex | **Supersedes** entirely (own DB, own cron) — but reopens the hosting problem #4 solved, since it needs a persistent host, not serverless |
